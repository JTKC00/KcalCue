規劃日期：2026-10-07  
狀態：設計提案；尚未實作、合併、部署或改變正式環境。  
主追蹤：JTKC00/KcalCue Issue #106 — Nutrition Journal & Insights roadmap

## 1. 產品定位與第一版目標

KcalCue 是以文字及結構化餐點紀錄為核心的營養日誌。AI 相片辨識只協助起草，使用者仍決定最終食物、份量及手動熱量。

第一版要完成：

> 不用相片、不呼叫生成式 AI，也可以手動記一餐、加備註、找回舊餐點，並查看有清楚資料限制的 7／30 日統計。

沿用目前 Private Beta；Free core + metered AI 為未來方向，本期不實作收費或開放註冊。相片永久保存繼續由 #62 延後追蹤。

本文件所有欄位上限、分期及新 UI 文案均是建議設計，不是已上線功能。

## 2. 已核對的現有基礎

目前 source 已有：

- MealDraft／MealRecord：日期、時間、時區、早餐／午餐／晚餐／小食、食物與份量、原始 AI 分析、使用者修正、版本及 mutation 資料。
- `mealCalories()`：手動熱量優先；未知個人份量與不足營養資料不當完整餐點估算。
- `dayCalories()`：熱量範圍及 manual／reference／partial／unknown／invalid 計數。
- Today／History：每日摘要、餐點編輯及單一日期篩選。
- IndexedDB 草稿與 outbox、依 UID 的資料隔離、衝突處理、刪除 tombstone。
- 分頁同步：組齊同一 revision 的所有頁面才提交新本機 snapshot。

目前待新增：meal-level 日誌備註、History 關鍵字／餐次／日期範圍查找、跨日統計 domain、Insights 頁。

需要刻意改善：Today 在已知沒有餐點時，現有 UI 同時顯示 0 餐及 0 kcal。第一版保留「0 餐」，將熱量改為「尚無記錄」，避免與「實際攝取 0 kcal」混淆。

重要區別：不是完全不用雲端儲存；既有 Firestore 繼續保存餐點／文字。本期不新增相片物件儲存。

## 3. 範圍

### 本期必做

1. 手動記餐成為清楚可見的主要入口，保留 AI 相片辨識入口。
2. 每餐可選的純文字備註；編輯、儲存、同步、重新開啟後保留。
3. 日誌沿用 History：日期範圍、餐次、食物及備註關鍵字查找。
4. Today／最近 7 日／最近 30 日的確定性統計。
5. 熱量趨勢、蛋白質／碳水／脂肪摘要、餐點及記錄日數、餐次分布。
6. 資料不足、尚未同步、衝突、載入中的可見狀態。
7. 可讀文字摘要及圖表的表格替代呈現。

### 延後

- 複製舊餐點、常吃餐點、收藏、自訂標籤。
- 全日反思、心情／飽足感追蹤、日記完成打卡。
- 使用者目標、體重、熱量預算、週期比較、移動平均、中位數。
- AI 長期飲食分析／聊天教練。
- 相片永久保存、公開註冊、付款、訂閱、credits 實作。

中位數及比較並非放棄，而是先避免一個小螢幕同時出現過多不同分母的指標。

## 4. 使用流程與資訊架構

沿用現有 hash navigation；History 的既有入口保持可用，新增 `#insights`。

主要目的地：今日／新增／日誌／統計；帳戶與安裝保留現有獨立入口。

### 今日

顯示日期、記錄餐數、已記錄熱量、主要營養素及資料狀態。主要操作是「手動記一餐」，旁邊保留「用 AI 辨識」。空白日顯示「今日未有記錄」，不評斷使用者吃得好或不好。

### 新增與編輯

沿用食物項目、份量、日期時間及餐次欄位，新增選填備註。

至少有一項食物才是餐點；份量／營養可以未知。不要要求使用者拍照或先取得 AI 結果才可儲存。

純備註不產生一筆空餐，也不自動拆解成食物。使用者只在備註寫「少飯」時，營養不自動改變；要改營養，需修改食物或份量欄位。介面應直接說明這點。

### 日誌

以日期分組，顯示餐次、食物、已確認的份量／熱量、備註摘要、同步狀態。篩選可以組合：日期範圍 AND 餐次 AND 關鍵字。

關鍵字只搜尋目前使用者最終食物名稱與備註，不搜尋原始 AI 誤認名稱、不跨帳戶。採簡單本機文字比對；本期不建全文搜尋服務或同義詞系統。搜尋字串不是正則表示式。

日誌篩選只影響日誌列表；不默默改變 Insights 的全期間指標。UI 要能清除所有篩選，區分「沒有符合條件的餐點」與「沒有任何餐點」。

### 統計

次序：期間切換 → 記錄日數／餐數／資料狀態 → 熱量趨勢 → 已記錄熱量平均 → 營養素摘要 → 餐次分布 → 查看日誌。

點擊某日進入該日記錄。375 px 寬可操作；30 日圖表減少軸標籤但保留逐日讀值。圖表不只靠顏色區分未知／不完整／待同步，並提供逐日文字表格。

## 5. 日誌欄位合約

建議欄位：`journalNote?: string | null`。

- 純文字；上限建議 500 個 Unicode code points，前後端採同一計數法，並有有限 request byte 上限。
- 允許換行；換行正規化；不接受 HTML 或富文字，不自動執行或呈現可操作內容。
- 超長時清楚拒絕儲存並保留原始草稿，不靜默截斷。
- 新增：空白正規化為 null。
- 修改請求省略欄位：保留原有備註，代表舊版 client 沒有編輯此欄。
- 明確 null：清除備註。
- 舊紀錄缺少欄位：顯示沒有備註，不虛構舊文字。
- 備註只存在使用者草稿／餐點資料，不加入診斷 log、分析事件、URL、GitHub 或 AI payload。

備註修改使用既有 version／mutation／outbox 流程。變更備註必須改變 writable-command fingerprint；同一份內容重試沿用同一 mutation，不能令已成功的舊 mutation 吃掉新備註。

只修改備註不改食物基礎，不清除有效的 `calorieCorrection`，不改寫原始 analysis／originalItems／analysisProvenance，不發起額外 vision 或外部營養查詢。

## 6. 舊版相容與回退

目前餐點 schema 為 5，而 server 的 `commitMeal()` 會組出完整 saved record 後寫入。新增備註不是只加 textarea；舊 writer 不知道新欄位時存在遺失風險。

建議採相容橋接發佈：

1. 先增加新欄位讀寫／省略保留／明確清除及下一版 schema 的支援，仍不在 UI 開放新備註輸入。
2. 新 server 接收舊 client 請求時，在 versioned transaction 內保留現有備註，並保存原本衝突語意。
3. 舊 snapshot／草稿／outbox 可讀，省略欄位不能被 client 提早轉成「明確清除」。
4. 對新備註資料採下一個受保護的餐點 schema，基準下預定 6；實作前重新核對是否有其他 schema 變更。
5. 未使用新功能的既有文件不作全庫重寫；以新增或實際修改餐點逐步升級。
6. 開放 UI 前，指定能保存新欄位的相容 revision 作 rollback target；不能僅因舊 revision Ready 就認定可安全回退。
7. 新 UI 要核對 server 能處理備註，並驗證 save ACK 的新欄位／schema。遇舊 server 不理解、ACK 沒保留備註、或 unsupported schema 時，顯示失敗並保留草稿，不能清空後宣稱成功。
8. 舊 RC 寫入路徑、已快取 PWA、離線舊分頁與回退版本均列入 release 檢查，不靠重新登入假定已解決。

正式橋接部署與最終部署均需獨立授權。本規劃沒有部署任何內容。

## 7. 統計規則

### 7.1 統計描述的是「已記錄內容」

必須分開三種完整度：

- 同步快照是否完整：是否已取得可信的一整份餐點清單，而非僅第一頁。
- 已記錄餐點的營養欄位是否可計算：熱量與各營養素分開判斷。
- 使用者是否真的記齊全日飲食：第一版不知道，不能由三餐、熱量高低或有記錄日數推斷。

因此可以寫「7 日內有 5 日有記錄」「12 餐中有 9 餐有完整熱量資料」，不能寫「飲食記錄完整度 90%」「已完整記錄 5 日」。

### 7.2 熱量

- 沿用 `mealCalories()` 的手動覆寫、unknown、partial 與 reference 語意。
- 手動 kcal 是使用者提供的單值，不是量測證明。畫面標示來源。
- 有效的 0 kcal 與缺值、空白、未記餐分開。
- 原始 AI 分析不進入最終統計。
- 範圍逐餐相加，保留上下界；只在最後呈現時向外取整。
- 範圍不是統計信賴區間，不能稱 95% 信心或用中點假裝精確。
- 某餐個人份量未知且沒有有效手動熱量時，沿用整餐未知保護。
- 可顯示已知部分的合計，但必須標出被排除的未知／不足餐數，不能稱全日攝取總量。

### 7.3 平均值

第一版只提供一個明確的日平均，不同時計算各種分母版本。

日平均的 eligible days：在所選期間內、已過去的日期（排除仍進行中的今日）、至少一筆餐點、所有已記錄餐點有完整熱量資料、且沒有未解決同步／衝突項目的日期。

- 有效手動 kcal 可作該餐完整熱量輸入，不代表 macros 也完整。
- partial／insufficient／none／invalid 的日子不納入主平均，顯示排除日數。
- 無記錄日不是 0，從分子與分母排除。
- 0 個 eligible days：顯示資料不足，不回傳 0。
- 只有 1 個 eligible day：顯示該日數值與樣本不足，不顯示跨日平均結論。
- 多個 eligible days：上下界分別求平均，並明列分母。
- 即使所有已記錄餐點都有 kcal，也不能推斷使用者記齊全日飲食。

示意：兩個符合條件的已過去日期分別記錄 1600、1800 kcal，第三天沒有記錄；平均是 1700 kcal，分母是 2 日。這不是三天實際飲食平均，也不是飲食目標。

圖表仍可顯示今日暫計與不完整日，只有主平均採較嚴格篩選。

### 7.4 蛋白質／碳水／脂肪

逐餐計算後依日期聚合，保存各項目可用性與被排除計數。不要先將全期食物攤平成一餐再以整體 coverage 蓋過某餐未知份量。

- 有 kcal 不代表有 macros。
- 不從使用者的熱量修正倒推蛋白質／碳水／脂肪。
- 有參考 macros 而使用者覆寫 kcal 時，分別保留來源，不強制令兩者對齊。
- 第一版顯示已知克數範圍與涵蓋餐數；完整營養素日平均採該營養素自己的 eligible days。
- 沒有可用營養素時顯示未知，不顯示 0 g。
- 本期不做以手動 kcal 為分母的 macro 能量百分比圓餅圖。

### 7.5 期間與日期

- 最近 7／30 日為包含目前參考日的連續 calendar days，不是最後 7／30 筆餐點。
- 畫面明示實際起訖日期；今日標示進行中。
- 按使用者已儲存的餐點 `date` 分組；保留 `time`／`timezone` 作語境。
- 旅行後不因裝置換時區而把舊餐點移到另一日。
- 以注入的 reference date 計算測試；跨月、跨年、閏日、DST 及 23:59／00:00 有回歸。
- future-dated records 在相應日期到來前不計入以今日為止的期間；日誌仍可找到。

### 7.6 來源與同步

- 沿用相同 UID 下的 `visibleMeals(SyncState)` 合併語意，按 meal ID 一餐只計一次。
- 尚未明確儲存的編輯草稿、demo 及已刪餐點不納入。
- 已按儲存但待同步的本機餐點可在逐日圖／列表暫計，必須顯示 provisional 狀態；不宣稱已在雲端。
- 同步錯誤／衝突的餐點與受影響日期顯示待處理；不進入主平均。日誌與圖表引用同一份帶狀態的 resolved snapshot，避免兩邊偷偷選不同版本。
- 刪除待同步時從本機可見合計移除，並標示待同步；放棄刪除／同步衝突後重算。
- 沒有成功的完整雲端 snapshot 時，不把本機局部清單描述成完整 30 日統計。
- 分頁失敗時保留上次完整 snapshot，標示過期／未同步，不用已讀第一頁覆蓋。
- 切換帳戶／登出立即隱藏舊圖表、舊摘要、搜索內容及筆記，晚到回應不得恢復舊 UID 資料。

## 8. 架構與成本

建議分層：

`現有餐點/同步層 → 帶同步狀態的分析輸入 → 純函式聚合 → 今日/Insights/文字摘要`

新增純函式模組可使用 `src/lib/insights/`；UI 拆成小元件，不把所有統計繼續塞入 `meal-journal.tsx`。純函式接收資料、期間、reference date 及狀態，不能自行 fetch、讀 Firebase、呼叫 AI 或使用隱藏全域帳戶狀態。

Statistics 不存第二套權威 totals，不新建統計 collection／scheduler／Cloud Function。第一版直接重用既有完整同步資料，在本機重新聚合。修改／刪除後重算，避免餐點與持久摘要不一致。

切換期間、搜尋和開關圖表不增加 meal GET、Firestore listener、AI 或外部營養查詢；原本同步計時器不因此增頻。一般雲端同步／儲存仍有成本，不能稱整個產品零成本。

#89 的舊版／revisionless full-read 問題仍然 open。第一版不以加圖表為由靜默截斷歷史，也不順便做未授權遷移。大型帳戶若需要 date-range server queries，另行設計 coverage／cursor／index／費用與舊版兼容。

## 9. 分 PR 與發佈順序

這是計劃名稱，不是已建立的 PR。

| 順序 | 工作 | 完成條件 |
| --- | --- | --- |
| J1a | Notes compatibility foundation | 型別／schema／API transaction／cache／outbox／ACK 舊新兼容通過；暫不開新輸入 UI |
| J1b | Journal-first UI | 手動入口清楚；備註新增／修改／清除／reload；有效手動 kcal 不因筆記編輯消失 |
| J2 | Deterministic statistics | 7／30 日聚合、各種缺值／範圍／分母／同步狀態的純函式測試 |
| J3 | Insights UI + Today 一致性 | mobile 圖表與文字表；空白日不是 0 kcal；各頁與 domain 結果一致 |
| J1c | History search & filters | 食物／備註關鍵字、餐次及日期範圍查找；篩選不偷偷改 Insights |

J1a 先完成並驗收相容橋接版，再以它作最終 v1 的回退基礎。其餘 PR 逐個合併已審查內容，避免多條舊分支相互堆疊；不要求每個小 PR 都另行 live deploy。最終整合版走一次完整 release acceptance。

每個 PR 的停止點：實作、受影響測試、獨立 review、精確 HEAD 報告。merge 與 production rollout 分開授權。若派 Cursor subagent，使用 Cursor 模型，不改派其他模型；驗收 Bot 只用指定 QA 帳戶。

## 10. 驗收矩陣

### 資料與相容

- 舊紀錄沒有備註可讀可改；舊請求省略欄位不刪新備註。
- 新增、修改、清除、空白、換行、emoji、上限／超長、HTML-like 純文字。
- note-only 修改保留 kcal correction、原始分析與其他餐點資料。
- note-only 修改不發起 AI／外部營養解析。
- 同 mutation 同 payload 不重複；變更備註不可錯用已 ACK 的 mutation。
- 舊 PWA、舊 outbox、新 server；新 client、舊 server；相容回退路徑。

### 聚合

- 無餐點／未知餐／partial／insufficient／有效 0／非法手動值／reference 範圍。
- 有手動 kcal 沒有 macros；手動 kcal 與 reference macros 各自來源。
- 未記日、今日未完、只有一個樣本日、所有日不符合平均條件。
- 日期區間／時區／跨日／跨月；重複 ID／demo／刪除餐點。
- 聚合前不多重 rounding；上下界有限且 min ≤ max。
- 修改一餐、變日期、改餐次、刪餐後，當日／全期結果一致更新。

### 同步、私隱與效能

- 先有完整 snapshot，再分頁失敗，不把部分頁當成完整歷史。
- 合成超過一頁資料（例如 101／201 筆）及較大本機資料集。
- 離線儲存→重連→ACK，計數不重複，pending 標示正確。
- blocked-save／conflict 不變成成功雲端紀錄或穩定平均。
- A→B、A→B→A、跨分頁登出、晚到 response：舊帳戶圖表／備註不閃現。
- 切 7／30 日及搜尋不額外發起讀取／AI；用實測記錄成本路徑，不宣稱未量測的性能數字。

### UI 與 hosted

- 375×812 及桌面；所有主要控制可達、文字可讀、沒有橫向溢出。
- 確認無照片、無 vision request 仍可完成手動記餐→備註→儲存→日誌→統計。
- 用合成 QA 餐點驗證 exact authenticated API readback，不只看 UI Toast。
