# Unknown personal serving (meal schema v5)

When a photo identifies food but cannot establish how much the user personally ate or drank, the AI observation stores `portionMin: null` and `portionMax: null` together. A numeric pair remains valid for older analyses. One-sided null and inverted or nonpositive ranges are rejected. The prompt asks for null only when the personal serving is genuinely unobservable; it does not turn every approximate serving into unknown.

The editable meal item preserves that pair and its original AI values separately. The user can enter a positive range later or clear both fields. An unknown item skips nutrition lookup and contributes no kcal or macros. If any item has an unknown personal serving, the reference whole-meal kcal remains unknown even if other foods have usable reference data. An explicit whole-meal user kcal correction remains possible and is labelled as user-entered. Today does not add an incomplete subtotal as a full meal.

New cloud writes use `schemaVersion: 5` and retain an explicit `photoRef`, including `null`. Existing versions 0–3 and photo version 4 are readable/editable by the new writer; edits upgrade to v5 without changing the original AI analysis or creation time. The new photo reader accepts valid v4 and v5 references. The old writer's version gate rejects v5 writes; rolling the backend back after v5 records exist therefore needs a writer that understands both nullable portions and the photo lifecycle. No destructive data migration is needed.

Local verification on 2026-09-28: typecheck, lint, build, 626 unit tests, 90 Firestore emulator tests including null save/read/correction and v4 photo upgrade, and 25 browser E2E tests at 375px including a real-photo fixture with mocked AI. Independent QA found a stale name-lookup race and a mislabeled future-schema test; both were corrected and independently rechecked. These checks do not establish that the current production model actually emits null when appropriate, or that this unmerged code is deployed.
