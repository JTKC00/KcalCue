# Unknown personal serving (introduced in meal schema v5)

When a photo identifies food but cannot establish how much the user personally ate or drank, the AI observation stores `portionMin: null` and `portionMax: null` together. A numeric pair remains valid for older analyses. One-sided null and inverted or nonpositive ranges are rejected. The prompt asks for null only when the personal serving is genuinely unobservable; it does not turn every approximate serving into unknown.

The editable meal item preserves that pair and its original AI values separately. The user can enter a positive range later or clear both fields. An unknown item skips nutrition lookup and contributes no kcal or macros. If any item has an unknown personal serving, the reference whole-meal kcal remains unknown even if other foods have usable reference data. An explicit whole-meal user kcal correction remains possible and is labelled as user-entered. Today does not add an incomplete subtotal as a full meal.

Schema 5 introduced nullable personal portions and retained an explicit `photoRef`, including `null`. The journal-note compatibility bridge later advances new writes to schema 6 while preserving the same nullable-portion behavior. Existing versions 0–3, photo version 4 and nullable-portion version 5 remain readable/editable by the current writer; an actual write upgrades the record to the current schema without changing the original AI analysis or creation time. The photo reader accepts valid v4, v5 and current-schema references. Older writers continue to fail closed on schemas they do not understand, so rollback after newer protected fields exist requires a compatible writer. No destructive data migration is needed.

Independent QA found a stale name-lookup race and a mislabeled future-schema test; both were corrected and independently rechecked. These checks do not establish that the current production model actually emits null when appropriate, or that this unmerged code is deployed.
